01 — The problem

Recovery is usually a spreadsheet someone forgets to open.

Failed subscription payments quietly leak revenue every day — a declined card, a timed-out gateway, an expired auth. Most teams handle this manually, inconsistently, or not at all. The ones who automate it often can't say why the system did what it did, which makes it unsafe to trust with real money.

02 — How it works

Four stages. Every one of them logged.

01

DIAGNOSE

Classifies the raw failure code into a root cause — rule-based first, LLM fallback for the ambiguous ones. Every classification is explainable.

02

DECIDE

Picks exactly one bounded action. Hard stopping rules first: never retry a fraud-flagged card, max 3 retries, low-confidence → human.

03

EXECUTE

Creates a real Razorpay test-mode payment link via the API and sends a Hinglish reminder. No silent auto-charging — that's not how card networks work.

04

LOG

Every decision, reason, and outcome is written to an audit trail. Nothing is deleted, nothing is hidden after the fact.

03 — Measured, not claimed

Results from a 75-case synthetic batch.

Synthetic failure data, modeled on real Razorpay webhook failure codes — because no buildathon team has access to a live merchant's failure history. What's not synthetic: the diagnosis logic, the decision rules, the audit trail, and the Razorpay API calls.
